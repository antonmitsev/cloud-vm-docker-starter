# Как стигнахме от празен Google Cloud проект до работещ HTTPS адрес

Това е човешкият запис на стъпките, през които минахме на **24–25 октомври 2026 г.** Настройвахме услугите ръчно през уеб конзолата и Cloud Shell. Terraform файловете в проекта не са използвани за създаването им.

Целта беше да подготвим малка VM за бъдещо приложение: собствена мрежа, ограничен SSH достъп, отделен диск за данни, Docker, HTTPS, резервни копия и известяване при проблем. Засега на VM работи само Caddy с начална страница и адрес `/health`; самото приложение предстои.

## 1. Проект, плащане и бюджет

В Google Cloud създадохме проект с ID `example-project-id`. Създадохме billing account и го свързахме с проекта. Това позволи създаването на платени ресурси.

В **Billing → Budgets & caps** настроихме месечен бюджет **$26.50** за billing account с прагове **50%, 90%, 100% и 150%**. Това са известия за разходите. Те не спират VM автоматично, когато сумата бъде достигната.

Преди да създадем машината, сравнихме регионите в калкулатора на Google Cloud. Избрахме **Белгия (`europe-west1`)**, зона **`europe-west1-b`**. Калкулаторът показваше около **$15.45 на месец** за разглежданата VM конфигурация с boot disk. Отделният data disk, публичният IPv4 адрес, snapshots, Cloud Storage и трафикът трябва да се следят отделно в реалния billing отчет. Числото **730 часа** в калкулатора означава приблизително цял месец непрекъсната работа.

## 2. Собствена мрежа

В **VPC network → VPC networks** създадохме мрежа `cloud-app-vpc` и subnet `cloud-app-subnet` с диапазон `10.42.0.0/24`. VM беше включена в тази мрежа, вместо в автоматичната `default` мрежа. Вътрешният ѝ адрес стана `10.0.0.2`.

В **VPC network → Firewall** добавихме две входящи правила. И двете са насочени към мрежовия tag `cloud-app-server`, който после поставихме на VM:

| Правило | Източник | Разрешен трафик | Защо |
| --- | --- | --- | --- |
| `cloud-app-iap-ssh` | `35.235.240.0/20` | TCP 22 | SSH през Google Cloud IAP. |
| `cloud-app-web` | `0.0.0.0/0` | TCP 80 и 443 | Публичен HTTP и HTTPS достъп до Caddy. |

Оставихме приложението и бъдещата база данни без публични портове. При създаването на VM не използвахме автоматичните отметки **Allow HTTP traffic** и **Allow HTTPS traffic**: вече имахме конкретно правило `cloud-app-web`, което работи чрез tag.

## 3. Постоянен публичен адрес

В **VPC network → IP addresses** резервирахме статичен външен IPv4 адрес с име `cloud-api-ip`: **`203.0.113.10`**. Прикачихме го към VM. Така DNS A записът може да сочи към адрес, който няма да се смени при обикновен рестарт на машината.

## 4. Самата VM

В **Compute Engine → VM instances → Create instance** създадохме `cloud-app-vm` в `europe-west1-b`. Избрахме Ubuntu 24.04, машина **`e2-small`**, provisioning model **Regular** и 20 GiB **Balanced persistent disk** за операционната система. `e2-small` се показва с **0.5 vCPU и 2 GiB RAM**; когато зададохме ръчно 2 ядра, калкулаторът избра друг тип машина. `Threads per core: 2` оставихме по подразбиране.

В раздел **Networking** премахнахме предварително добавения интерфейс към `default` мрежата и оставихме един интерфейс към `cloud-app-vpc` / `cloud-app-subnet`. Избрахме запазения външен адрес `cloud-api-ip` и поставихме tag `cloud-app-server`. **Alias IP ranges** остана празно; не ни трябваше допълнителен IP диапазон. Оставихме системния hostname по подразбиране.

В раздел **Security** избрахме service account `cloud-app-vm@example-project-id.iam.gserviceaccount.com` и вход чрез **OS Login**. На VM са избрани пълни Cloud API access scopes, а конкретните разрешения за услуги се управляват и чрез IAM роли. Не добавихме ръчно SSH ключове в настройките на VM. Административният достъп минава през IAP.

## 5. Отделен диск за данните

Създадохме и прикачихме отделен **20 GiB Balanced persistent disk** с име `cloud-app-data`, в същата зона като VM. За него зададохме **Keep disk** при изтриване на VM, така че подмяна на машината да не изтрие автоматично данните.

След SSH вход в машината проверихме дисковете. Новият празен data disk беше `/dev/sdb`; boot disk беше `/dev/sda`. Форматирахме **само `/dev/sdb`** като ext4 и го монтирахме на `/srv/cloud-app-data` по UUID:

```text
00000000-0000-0000-0000-000000000000
```

`findmnt /srv/cloud-app-data` показа `/dev/sdb` с ext4, а `df -h /srv/cloud-app-data` показа приблизително 20 GiB пространство. След рестарт на VM монтирането остана налично. Това е дискът, на който Caddy пази постоянните си данни и където по-късно ще сложим данните на приложението.

## 6. Достъп до VM и Docker

Използвахме **Cloud Shell** за `gcloud compute ssh` през IAP. Cloud Shell е терминал извън VM; когато SSH командата ни свърже, чак тогава командите се изпълняват на `cloud-app-vm`.

```sh
gcloud compute ssh cloud-app-vm \
  --project=example-project-id \
  --zone=europe-west1-b \
  --tunnel-through-iap
```

При първото свързване `gcloud` създаде SSH ключ. Ключът може да поиска пасфраза при следващ вход. Пасфрази и частни ключове не записваме в Git.

На VM инсталирахме Docker Engine и Docker Compose. По време на проверката версиите бяха **Docker Engine 29.9.2** и **Compose 5.6.1**. Проектът е в `/srv/cloud-vm-docker-starter`; реалният `.env` задава `APP_DOMAIN=api.example.com` и не е качен в Git.

## 7. DNS A запис и HTTPS

В DNS управлението на `example.com` добавихме **A запис**:

```text
Име:      api
Тип:      A
Стойност: 203.0.113.10
```

Така `api.example.com` започна да сочи към статичния адрес на VM. Стартирахме `gateway` услугата от `compose.yaml`. Caddy видя домейна, издаде HTTPS сертификат автоматично и започна да обслужва адреса през порт 443. Данните за сертификата са на прикачения data disk, за да оцелеят при пресъздаване на контейнера.

Началната страница `https://api.example.com/` връща `Cloud VM ready`. Добавихме отделен адрес `https://api.example.com/health`, който връща **HTTP 200** и текст `healthy`. Непознатите пътища са конфигурирани да връщат **404**. Това е в Git комит `07e7c8c` и е приложено на VM с пресъздаване на `gateway` контейнера.

## 8. Bucket и ръчен тест на резервно копие

В **Cloud Storage → Buckets** създадохме частен bucket `example-project-id-cloud-app-backups` в `europe-west1`, със Standard storage, uniform bucket-level access, public access prevention и 7-дневен soft delete.

Дадохме на VM service account роля **Storage Object Creator** само за този bucket. Тя позволява създаване на обекти, без общ достъп до останалите buckets. При пробата `gcloud storage cp` от VM върна **403** за `storage.objects.get`; този инструмент се опита да чете обект, а текущата роля не дава такова право. Използвахме Cloud Storage JSON API `objects.insert` за upload с write-only права и създаването проработи.

Качихме и пробна SQLite база `sqlite-probe-20261024T220159Z.sqlite`. Отделно, през Cloud Shell с операторски права, я изтеглихме и отворихме. `PRAGMA integrity_check` върна `ok`, а пробният запис — `backup-ok`. Това доказа ръчно, че можем да качим и възстановим **пробен** SQLite файл. Автоматичен backup на истинско приложение още няма.

## 9. Snapshot графици

На `cloud-app-data` добавихме дневен snapshot график `cloud-app-data-daily` със **7 дни** съхранение. За boot disk конзолата показваше график `default-schedule-1` с **14 дни** съхранение. Не включихме **application consistent snapshot** за data disk, защото бъдещата SQLite база ще има отделен, съгласуван backup процес. Не сме правили пробно възстановяване от snapshot.

## 10. Наблюдение и известяване

В **Monitoring → Uptime checks** настроихме `cloud-app-https` да проверява HTTPS адреса `api.example.com/health`. Успешният отговор трябва да е **200** и да съдържа `healthy`. Настроихме и имейл известяване; по време на настройката получихме мейл за грешка, което потвърди доставката на известия.

Проверката в момента показва дали **Caddy** работи. Когато добавим приложение, ще запазим същия публичен `/health`, но ще го свържем с проверка на самото приложение. Така няма да променяме URL адреса в Monitoring.

## Къде спряхме

Имаме работеща VM, ограничен административен достъп, собствена мрежа, постоянен диск, Docker, домейн с HTTPS, ръчно проверен път за backup и uptime известяване. **Приложението и истинската му база още не са внедрени.** Следващата работа е внедряване на приложението, автоматичен SQLite backup и проверка на възстановяването му.

За точните имена на ресурсите, UUID и техническите проверки виж [инвентара на реалната среда](gcp-current-state.md). За ново внедряване или възстановяване виж [VM ръководството](google-cloud-vm.md) и [операциите](operations.md).
