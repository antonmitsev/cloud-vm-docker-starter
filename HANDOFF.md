# Хендоф — Cloud VM Docker Starter

**Дата:** 31 октомври 2026 г.

**Следваща сесия:** проверка на подновяването на Caddy origin сертификата

**Източник за облачния статус:** [отчетът от последната проверка на 25 октомври](docs/gcp-current-state.md), публичните проверки и прочитът на сертификата от VM на 31 октомври. Това не е нова проверка през GCP API.

Този файл заменя стария хендоф от 21 октомври извън репото. Първоначалната задача за създаване на VM вече е изпълнена ръчно.

## Състояние

- В GCP е създадена една Ubuntu 24.04 `e2-small` VM в `europe-west1-b`, със собствена VPC, статичен IPv4, IAP/OS Login и отделен 20 GiB data disk, монтиран по UUID на `/srv/cloud-app-data` и настроен да се запази при изтриване на VM.
- Docker Compose стартира Caddy. Публичният API поддомейн минава през Cloudflare for SaaS към VM; уеб firewall правилото допуска само Cloudflare IPv4 диапазони. `/` връща `Cloud VM ready`, а `/health` — `200 healthy`. Засега `/health` проверява Caddy.
- Има частен backup bucket, snapshot график за data disk, показан в конзолата график за boot disk, ръчен SQLite upload/download/restore тест с `integrity_check=ok`, uptime проверка и billing alerts. Няма внедрено приложение, истинска база или автоматичен SQLite backup.
- Terraform черновата в `infra/` не е прилагана и няма import state. Уеб правилото в HCL още допуска `0.0.0.0/0`, а примерният регион е `europe-west3`. Cloudflare, snapshots, monitoring и backup задачата не се управляват от тази конфигурация. [Разликите и евентуалният import път](infra/README.md) са документирани; Terraform не е непосредствената следваща стъпка.
- На 26 октомври GCP насоките и Terraform документацията бяха одитирани и синхронизирани; комит `75292ea` е качен в `origin/main`. Не са правени промени в GCP или функционални промени в Terraform ресурсите.
- На 31 октомври операторът потвърди, че Cloudflare TLS режимът е **Full (strict)**. Публичният `/health` върна `200` през Cloudflare. Пробен несъществуващ `/.well-known/acme-challenge/` адрес по HTTP върна `308` към HTTPS; това показва отговор на порт 80, но не доказва успешно ACME валидиране.
- От VM през `127.0.0.1:443` прочетохме **Caddy origin сертификата** за API домейна. Той е валиден и е издаден преди Cloudflare cutover; все още няма доказано подновяване през Cloudflare. Точните му дати са само в локалния `.env.ops`.
- Прегледахме Caddy ACME логовете: Caddy получава и записва информация за предстоящото подновяване, без warning/error в извадката. Няма реален опит за подновяване или HTTP-01 challenge след Cloudflare cutover. Точният прозорец на CA е записан само в локалния `.env.ops`.
- В [операционното ръководство](docs/operations.md#check-caddys-origin-certificate-renewal) има VM команди за срока и ACME логовете, както и 14-дневен праг за бъдеща аларма. **Автоматична аларма за срока още не е настроена.** Публичната проектна страница казва, че следим двата сертификата; за origin това все още е план, а не действащо наблюдение.
- За boot реда е подготвен [примерен systemd drop-in](systemd/docker.service.d/10-require-data-disk.conf.example), който изисква монтиран data disk преди стартиране на Docker. Той **още не е инсталиран на VM** и не е проверен с нов рестарт. Нормалният рестарт на съществуващия Caddy контейнер продължава да се управлява от Docker `restart: unless-stopped`.
- Добавен е [чеклистът от нула](docs/from-zero-bg.md), започващ с Google акаунт, DNS и billing. Той описва нова среда, а не твърди, че всички стъпки са повторно изпълнени. Добавен е [start.sh](start.sh) за първо пускане на **подготвена** VM: тегли архива без `.git`, запазва локалния `.env`, проверява data disk и стартира Compose. Скриптът е проверен синтактично и конфигурацията на Compose е валидирана локално; **още не е инсталиран или изпълнен на текущата VM**. Следващата сесия да започне от този файл и локалния `.env.ops`.
- Подготвен е [план за отделен Node.js проект](docs/node-apps-bg.md): по един контейнер за `gaz` и `mas`, обща Docker мрежа с Caddy, маршрути по папки и отделни health проверки. Примерният Node код и Compose файл са проверени локално; временният Node `/health` върна `200 healthy`. Това е **документ за бъдещо внедряване**; Node проектът още не е създаден и `compose.yaml`/`Caddyfile` на живата инфраструктура не са променяни.
- По искане на оператора са добавени [две работещи учебни Node приложения](example-applications/README.md) в това репо: `gaz` и `mas` с отделни папки и контейнери, плюс локален Caddy demo. Кодът е bind mount, така че след редакция на `.mjs` файл се рестартира само съответният контейнер. Локално са проверени отговорите `hello from gaz`, `hello from mas`, двата health пътя и `404` за непознат префикс; Node портовете не са публикувани на host-а. Демонстрационните контейнери бяха оставени работещи за оператора на 31 октомври; при следваща сесия провери дали още работят. Няма внедряване на тези примери в облачната VM.

## Следващо

1. Следи origin сертификата през loopback поне седмично, а в посочения от CA прозорец от локалния `.env.ops` — ежедневно. Потвърди подновяването по **нова дата `notAfter` и успешни ACME логове**; проверка на edge сертификата или публичен `200` не е достатъчна. Настрой аларма, когато остават под 14 дни. Виж [командите](docs/operations.md#check-caddys-origin-certificate-renewal) и [сертификатите](docs/cloudflare-single-subdomain-bg.md#сертификати-и-подновяване).
2. Преди реални данни инсталирай подготвения boot guard на VM и провери с контролиран рестарт, че Docker стартира след монтирането на data disk. Следвай [операционната процедура](docs/operations.md#start-docker-only-after-the-data-disk). После добави периодичен SQLite backup извън VM, проверка за възрастта му и аларма при неуспех; повтори restore с реалната схема.
3. Добави метрики/аларми за памет и свободно място. При появата на приложение свържи публичния `/health` с неговото състояние.
4. Продължи със сървърното приложение: избери реалния runtime и схема, създай Docker image, вътрешна Compose услуга, backup и rollback процедура. Използвай [handoff за първо внедряване](docs/gcp-current-state.md#handoff-първо-внедряване-на-приложението). Cloudflare rate limit се определя след като са известни действителните API маршрути.

Преди каквото и да е `terraform apply` срещу този GCP проект са нужни live инвентар, съгласуван HCL и план за import. Не записвай истински домейн, IP, UUID, project ID, ключове или `.env` в Git. **Локалният `.env.ops` е игнориран от Git** и пази точните имена на GCP ресурсите, API домейна и командата за IAP вход с recovery SSH ключа от Cloud Shell; прочети го при следващ разговор, вместо да искаш имената отново. Започни от този файл, `.env.ops` и `git status`, после провери live състоянието, когато е нужен облачен достъп.
